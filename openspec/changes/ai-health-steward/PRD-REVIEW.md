整体判断：PRD 在架构决策和功能规格上已相当扎实，capability 切分清晰，决策有备选方案和理由。但作为一份要指导开发落地的 PRD，在**异常路径覆盖、可度量性、医疗合规细节、数据模型定义**四个方面存在明显缺口。这些问题不修复，工程师拿到后会在开发中途反复回来确认，医疗合规缺失则带来上线风险。

## 维度 1：完整性

PRD 包含 proposal（需求概述）、design（架构决策）、specs（功能规格）、tasks（版本规划），结构完整。但与标准 PRD 章节对照，以下内容缺失：

### 缺失章节

| # | 缺失内容 | 严重程度 | 说明 |
|---|---------|---------|------|
| 1 | 用户故事（As a... I want... So that...） | 中 | proposal 的 Why 提到了目标用户（本人+家庭），但没有结构化的用户故事。specs 里有 WHEN/THEN 场景，但缺少"用户是谁、想做什么、为什么"的叙事层，不利于设计同学理解上下文 |
| 2 | 非功能需求 | 高 | 完全缺失。没有性能要求（多模态抽取耗时预期？趋势图加载时间？）、安全要求（API key 如何存储？）、兼容性（浏览器范围？）、国际化。design.md 的 Open Questions 提了技术栈但未落到非功能需求 |
| 3 | 数据与埋点章节 | 中 | specs 里散落了数据模型线索（A-H 字段族、来源标记），但没有独立的数据模型定义章节，字段级定义缺失。埋点完全未提及 |
| 4 | 用户画像 | 中 | 目标用户"本人+家庭"过于笼统。谁是操作者？老人能直接用吗？家庭里谁负责上传报告？这些影响交互设计 |
| 5 | 成功标准与负向指标 | 高 | proposal 没有可度量的成功标准。design.md 的 Goals 列了功能性目标但无度量指标。作为开源项目，成功标准可能不是传统 DAU/留存，但也需要定义（如 GitHub star 数、fork 后部署成功率、issue 响应率） |

## 维度 2：清晰度

### 模糊描述清单

| # | 位置 | 模糊描述 | 建议澄清方向 |
|---|------|---------|------------|
| 1 | proposal "本地私有化部署" | "本地"边界不清——指服务部署在本地，但模型 API 调用走云端。design.md D6 和 Risks 里有解释，但 proposal 本身没说清 | 在 proposal 的 Why 或 What Changes 中补一句："本地指服务与数据私有部署，模型推理可走云端 API 或本地 LLM" |
| 2 | specs/health-profile "A-H 全字段族" | 字母代号 A-H 在 spec 里展开了一次，但后续引用时只说"B 字段族""D 用药记录"，读者需回查。且字段族的具体字段定义未给出（如 B 生理指标到底包含哪些指标字段、字段名/类型/单位） | 需要一份独立的数据模型定义，列出每个字段族的字段名、类型、单位、是否时序 |
| 3 | specs/ai-consultation "角色知识边界约束" | "角色设定和知识边界"具体指什么？是 system prompt 的内容约束？还是硬编码的意图白名单？design.md D3 提了概念但未定义边界内容 | 明确角色知识边界的实现机制和具体边界清单 |
| 4 | specs/visualization "参考范围" | 异常判定"基于参考范围"，但参考范围从哪来？是硬编码的医学标准？还是大模型判断？不同年龄/性别参考范围不同，如何处理？ | 明确参考范围的数据来源和个性化逻辑 |

### 术语未定义

| 术语 | 出现位置 | 问题 |
|------|---------|------|
| "操作者本人" | report-ingestion spec | 在单实例单家庭、无用户体系的架构下，"操作者"是谁？飞书渠道里是飞书账号，WebUI 里没有登录，"本人"如何确定？ |
| "人维度健康画像" | 多处 | 与"家庭成员档案"是同一概念吗？一个成员一个画像？ |
| "轻问答" | channels spec | 与"完整 AI 咨询"的边界在哪？哪些意图在飞书可用，哪些不可？ |

## 维度 3：边界覆盖

这是问题最多的维度。当前 specs 主要覆盖正常路径，异常路径和边界条件大量缺失。

### 遗漏的异常场景

| # | 能力 | 遗漏的异常场景 | 严重程度 |
|---|------|--------------|---------|
| 1 | report-ingestion | 多模态 API 调用超时或失败时的处理。design.md Risks 提了"降级提示"但 spec 里没有对应场景 | 高 |
| 2 | report-ingestion | 上传文件过大（如 50MB PDF）或损坏文件的处理 | 中 |
| 3 | report-ingestion | 多模态抽取结果为空或质量极低（如图片模糊、非医疗报告）时的处理 | 高 |
| 4 | ai-consultation | 意图路由器识别错误时的纠错机制。用户问"血糖 6.5 正常吗"可能被识别为"指标查询"而非"指标解读" | 高 |
| 5 | ai-consultation | 工具调用返回空数据（用户问"我的血压"但画像里没有血压数据）时如何回答 | 中 |
| 6 | channels/飞书 | 飞书 Bot 消息超时、回调失败、重复消息的处理 | 中 |
| 7 | health-profile | 多人同时编辑同一成员数据时的并发冲突（WebUI + 飞书同时写入） | 中 |

### 状态流转缺口

| # | 缺失的状态流转 | 说明 |
|---|--------------|------|
| 1 | 报告导入的状态流转 | 报告从"上传→抽取中→抽取完成→待确认→已入档/已拒绝"的状态机未定义。抽取中是否可取消？待确认状态有无超时？ |
| 2 | 聊天抽取确认的状态流转 | "系统识别出数据→询问用户→用户确认/拒绝/修改"的交互状态未明确。用户忽略确认提示怎么办？ |
| 3 | 家庭成员的状态 | 成员添加后能否修改基础信息？删除是软删除还是硬删除（spec 说"不可恢复"即硬删除，但数据溯源要求每条数据有来源，删除成员后溯源链断裂） |

## 维度 4：可度量性

### 不可度量的成功标准

proposal 和 design 完全没有定义可度量的成功标准。作为开源项目，建议至少定义：

| # | 缺失的度量 | 建议指标 |
|---|-----------|---------|
| 1 | 产品价值验证 | 无明确指标。建议：MVP 上线后 X 个家庭实际使用超过 2 周、健康画像平均数据条数 > N |
| 2 | 开源传播验证 | 无明确指标。建议：发布 3 个月内 GitHub star > N、fork > N、外部 issue/PR 数量 |
| 3 | AI 咨询质量 | 无明确指标。建议：AI 回答的用户确认率、意图识别准确率、用户修正抽取结果的比例 |
| 4 | 负向指标（护栏） | 完全缺失。建议定义：AI 误导性回答投诉率、数据丢失/错误率、多模态抽取失败率 |

## 维度 5：医疗合规

这是健康类产品最关键的维度，当前 PRD 在此维度有明显缺口。

### 合规遗漏清单

| # | 检查项 | 状态 | 说明 |
|---|--------|------|------|
| 1 | 内容安全合规标注 | 遗漏 | 业内健康 AI 产品普遍采用"S/A/B 风险等级标签体系"，本项目完全未提及。AI 生成的健康建议是否需要风险分级？如"建议停药"属于高风险，应触发预警 |
| 2 | 高风险预警机制 | 遗漏 | design.md Risks 提了"免责声明"，但免责声明是事后兜底，不是事前预警。当 AI 识别到高危信号（如胸痛描述、临界血压值）时，是否需要主动建议就医而非仅回答？ |
| 3 | 数据隐私与导出权 | 部分覆盖 | design.md 提了"隐私声明"和"数据本地存储"，但用户对自己健康数据的权利未定义：用户能否导出全部数据？能否删除单条记录（非整成员删除）？数据被模型 API 处理后，云端是否有留存？ |
| 4 | 医学边界 | 部分覆盖 | ai-consultation spec 的"角色知识边界约束"定义了"不做医疗诊断"，但边界不够细：症状咨询给出"可能的方向"算不算诊断？饮食/运动建议算不算？建议参考业内健康 AI 产品的边界定义 |
| 5 | 医学团队确认标记 | 遗漏 | 参考范围、异常判定阈值、用药相互作用知识——这些涉及医学专业判断的内容，是否需要标记"需医学团队确认"？当前 PRD 把这些当作可实现的功能，但数据源和准确性无保障 |
| 6 | 参考范围数据源 | 遗漏 | visualization 和 ai-consultation 都依赖"参考范围"做异常判定，但参考范围从哪来完全未定义。硬编码可能过时或不适用特定人群；大模型判断不可靠。这是医疗合规的关键依赖 |
| 7 | 模型 API 的数据处理政策 | 遗漏 | 不同模型 provider（OpenAI/DeepSeek）对发送内容的数据留存政策不同。开源项目需在文档中提示用户关注所选 provider 的数据政策，或推荐支持"零数据留存"的 provider |

## 维度 6：工程可实施性

### 工程视角的模糊点

| # | 模糊点 | 影响 | 建议 |
|---|--------|------|------|
| 1 | 数据模型未定义到字段级 | 工程师无法直接建表。A-H 字段族是概念分类，不是数据库 schema。每个字段族的表结构、字段名、类型、关系未定义 | 在 design.md 或独立数据模型文档中补充字段级定义 |
| 2 | 意图路由器的实现机制未定义 | 是用大模型做意图分类？还是规则匹配？还是两者结合？影响 V0.2 的技术方案设计 | 在 design.md 中补充意图路由器的实现方案 |
| 3 | 工具调用的接口定义未给出 | query_metrics / query_profile 等工具的输入参数、输出格式未定义。工程师不知道工具接口长什么样 | 在 ai-consultation spec 中补充工具的接口签名 |
| 4 | 向量库与结构化存储的关系未明确 | design.md D2 说"结构化为主+向量化辅助"，但两者如何关联？同一份数据存两份？向量化的是原始报告文本还是抽取后的摘要？查询时先查哪个？ | 在 design.md 中补充数据流向图 |

### 技术方案设计前必须澄清的问题

1. 技术栈选型（已在 Open Questions 中列出）
2. 结构化存储 + 向量库的选型与关联方式
3. 意图路由器的实现机制（模型分类 vs 规则匹配）
4. 多模态抽取的 JSON schema 形态（预定义 vs 自由输出）
5. 参考范围的数据来源与管理方式

## 常见陷阱扫描

| 陷阱 | 是否命中 | 说明 |
|------|---------|------|
| 孤立撰写（只有 PM 视角） | 是 | PRD 未见设计或工程输入痕迹。design.md 的 Open Questions 列了技术问题但未解决，说明尚未与工程对齐 |
| 无证据支撑（问题定义凭直觉） | 是 | proposal 的"为什么做"基于主观判断，无用户调研、行业数据或竞品分析支撑 |
| 方案过于规定性（写了怎么实现） | 否 | design.md 的决策是架构方向而非实现细节，边界把握得当。specs 聚焦"做什么"而非"怎么做" |
| 无护栏指标（只有成功指标） | 是 | 连成功指标都没有，更谈不上护栏指标 |
| 范围边界模糊（无不做的清单） | 否 | design.md Non-Goals 清晰，2 期清单也明确 |

## 评审结论

PRD 的架构思考质量高——capability 切分合理、七个决策有理由有备选、版本规划节奏清晰。但作为指导开发落地的文档，还不到"可以进入需求评审"的标准。

### 阻塞性问题（必须修复才能进入需求评审）

1. **数据模型未定义到字段级**——A-H 字段族是概念分类，工程师无法直接建表。需补充每个字段族的字段名、类型、单位、是否时序
2. **参考范围数据源未定义**——visualization 和 ai-consultation 都依赖参考范围做异常判定，但数据从哪来完全未知。这是医疗合规的关键依赖，必须在评审前确定
3. **异常路径大量缺失**——多模态失败、意图识别错误、空数据查询等核心异常场景未覆盖。specs 只有 happy path
4. **成功标准与护栏指标完全缺失**——无法判断产品做对了没有
5. **报告导入状态流转未定义**——从上传到入档的完整状态机缺失，包含中间态、超时、取消

### 建议性问题（建议修复但不阻塞）

6. 补充用户故事和用户画像，帮助设计同学理解上下文
7. 补充非功能需求（性能、安全、兼容性）
8. 明确"操作者本人"在无用户体系下的定义
9. 补充意图路由器和工具调用的接口定义
10. 补充向量库与结构化存储的数据流向图
11. 考虑软删除机制替代成员硬删除
12. 补充内容安全风险分级（S/A/B 标签体系）
