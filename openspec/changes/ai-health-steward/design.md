## Context

这是一个全新开源项目，目标是构建本地私有化部署的家庭 AI 健康管家。现有市场上的健康类 AI 产品（如讯飞晓医）多为闭源 SaaS，数据不在用户手中；而纯本地 LLM 方案在多模态健康报告处理上能力不足。本项目选择"私有化部署 + 云端模型 API 为主、本地 LLM 可选"的混合路线，在保证数据自主的同时获得多模态能力。

约束：
- 单实例服务一个家庭，不需要复杂多租户体系
- 开源项目，部署门槛要低，开发者 fork 后能快速跑起来
- 健康场景对 AI 输出安全性有要求，需角色知识边界约束
- 模型层需可插拔，支持多模态 API / 文字 API / 本地 LLM 三类 provider

## Goals / Non-Goals

**Goals**
- 健康数据结构化存入人维度画像，作为单一事实来源
- 多模态大模型驱动报告导入与结构化抽取
- 意图路由 + 工具调用的 AI 咨询，回答基于画像数据
- WebUI 为主界面，飞书渠道做资料收集与轻问答
- 家庭多成员档案隔离，报告归属可自动识别
- 第一梯队指标趋势可视化

**Non-Goals**
- 不做医院系统对接（HIS/电子病历直连）
- 不做可穿戴设备原生接入（2 期）
- 不做疫情数据查询（2 期）
- 不做多报告联合分析与时间序列对比（2 期）
- 不做移动端原生应用（后续考虑）
- 不做医疗诊断——AI 咨询仅作健康参考，不替代医生
- 不做多租户/多家庭隔离（单实例单家庭）

## Non-Functional Requirements

### 性能要求

| 场景 | 指标 | 目标值 | 备注 |
|------|------|--------|------|
| 多模态报告抽取（单页图片/PDF） | 端到端耗时（上传 → 结构化结果返回） | ≤ 15 秒（P95） | 含模型 API 调用，受 provider 延迟影响 |
| 多模态报告抽取（多页 PDF，≤ 10 页） | 端到端耗时 | ≤ 60 秒（P95） | 逐页抽取 + 合并 |
| 趋势图加载（单指标，数据量 ≤ 100 条） | WebUI 首屏渲染时间 | ≤ 2 秒（P95） | 含后端查询 + 前端渲染 |
| 趋势图加载（多指标同屏，≤ 5 指标） | WebUI 首屏渲染时间 | ≤ 3 秒（P95） | — |
| AI 咨询对话响应 | 首 token 返回时间 | ≤ 3 秒（P95） | 流式输出，含意图路由 + 工具调用 |
| AI 咨询对话响应 | 完整回答返回时间 | ≤ 15 秒（P95） | 含工具查询 + 模型生成 |
| 画像看板加载 | WebUI 首屏渲染时间 | ≤ 2 秒（P95） | 含成员列表 + 概览数据 |
| 飞书 Bot 消息响应 | 从用户消息到 Bot 回复 | ≤ 10 秒（P95） | 轻问答场景，含意图路由 |

### 安全要求

- **API Key 存储**：模型 API key 和飞书 Bot 凭证存储在服务端环境变量或 `.env` 文件中，不硬编码到代码仓库，不暴露给前端。`.env` 需加入 `.gitignore`
- **数据传输加密**：WebUI 与后端之间在本地部署场景默认 HTTP；生产部署建议用户自行配置 HTTPS（通过反向代理如 Nginx/Caddy）。后端调用模型 API 强制 HTTPS
- **健康数据存储**：所有健康数据存储在本地，不出服务器。仅对话内容和报告图片在调用云端模型 API 时会发送给 provider——需在隐私声明中明确告知用户
- **飞书回调安全**：飞书 Bot 回调需校验签名，防止伪造请求
- **输入校验**：上传文件类型白名单（图片 jpg/png/webp、PDF），文件大小限制（单文件 ≤ 20MB），防止恶意文件注入

### 兼容性要求

- **浏览器范围**：WebUI 支持现代浏览器——Chrome 100+、Firefox 100+、Safari 15+、Edge 100+。不支持 IE。移动端浏览器优先保证可查看，不保证完整功能可用
- **Docker 部署环境**：支持 Docker 20.10+ 和 docker-compose v2+。镜像基于 Linux x86_64 和 ARM64（适配 Apple Silicon）。最低配置建议：2 核 CPU / 2GB 内存 / 10GB 磁盘
- **模型 API 兼容**：多模态 API 支持 OpenAI 兼容接口（GPT-4o 等）、讯飞星火、DeepSeek 等主流 provider。文字 API 支持任意 OpenAI 兼容接口。本地 LLM 支持 Ollama 兼容接口
- **数据库**：默认 SQLite（零配置启动），可选切换 Postgres（面向数据量较大的场景）

### 国际化要求

- **中文优先**：MVP 仅支持中文界面和中文健康报告处理。所有 UI 文案、提示信息、错误消息默认中文
- **架构预留**：前端文案抽取为 i18n 资源文件（如 JSON key-value），不硬编码到组件中。后端多模态抽取 prompt 和角色设定支持通过配置切换语言。未来扩展英文等其他语言时无需改架构
- **日期与单位**：日期格式默认 `YYYY-MM-DD`，时区跟随部署环境。健康指标单位沿用报告原始单位，不做强制转换

## Decisions

### D1: 模型路由按输入类型分流，而非统一走多模态

**决策**：图片/PDF 输入必走多模态模型；纯文字输入（手动录入、聊天）走文字大模型。

**理由**：文字输入不必白调多模态能力，省 token、降延迟，且本地 LLM 兜底更容易（纯文字模型本地跑的门槛远低于多模态）。

**备选方案**：统一走多模态——被否，成本高且本地 LLM 无法兜底多模态线。

### D2: 健康画像以结构化存储为主，向量化辅助

**决策**：大模型抽取后输出 JSON 落库成结构化表（指标/诊断/用药等），支撑可视化与精确查询；原始报告文本和自由摘要走向量库，供 AI 咨询时语义检索（RAG）。

**理由**：可视化需要结构化字段才能画趋势图、做异常标识；纯向量存储无法支撑指标数值对比和排序。两者结合：结构化保精确，向量化保灵活。

**备选方案**：纯向量化 RAG——被否，可视化这一环会垮掉，无法画趋势图。

### D3: AI 咨询采用意图路由 + 工具调用，而非自由对话或 prompt 注入

**决策**：用户消息先经意图路由器识别意图，再调用对应工具（query_metrics / query_profile / extract_and_save 等）获取结构化数据，最后由模型基于工具返回结果生成回答。角色知识边界约束兜底超出能力范围的问题。

**理由**：
1. 符合 AI 工具发展方向（function calling / tool use）
2. 结构化画像已落库，就该用工具精确查询，而非塞进 prompt 让模型猜
3. 对用户更好——回答基于真实数据而非模型推断，准确性可控
4. 可审计——每次回答可追溯到调用了哪些工具、读了哪些数据

**备选方案**：
- 自由对话 + RAG 检索——被否，回答质量看运气，健康场景不可控
- prompt 注入画像摘要——被否，token 开销大且画像过大时截断丢信息

### D4: WebUI 与渠道职责分离，而非平级

**决策**：WebUI 是主界面承载完整功能（可视化、上传、录入、完整对话）；飞书渠道只做资料收集（发图->抽取->入档->回复确认）和轻问答（复用意图路由，但不渲染复杂图表）。

**理由**：飞书渠道交互能力有限，强行渲染趋势图体验差；让飞书做"随手丢+随口问"，WebUI 做"坐下来看和管理"，分工自然。

**备选方案**：渠道与 WebUI 平级——被否，每个渠道都要完整适配，工作量大且体验难统一。

### D5: 报告归属采用"默认本人 + 多模态姓名识别 + 手动覆盖"组合

**决策**：飞书渠道收到报告时默认归本人；多模态抽取时顺带识别报告上的姓名，匹配家庭成员则自动归属；用户可在交互中手动指定覆盖。

**理由**：纯手动询问太繁琐；纯账号绑定不够灵活（一个飞书账号可能代传多人的报告）。组合方案对用户最自然，代价是多模态 prompt 增加姓名识别任务 + 一个姓名匹配逻辑，都不重。

**备选方案**：
- 飞书账号 = 单一成员——被否，家庭多人需多 Bot
- 每次询问——被否，交互多一步繁琐

### D6: 模型层三类 provider 抽象，多模态 API 为必选依赖

**决策**：模型层抽象为三类 provider——多模态 API（必选）、文字 API（可选）、本地 LLM（可选）。provider 通过统一接口定义，配置切换。本地 LLM 只能兜文字线，多模态线本地基本跑不动，需在文档中说明。

**理由**：多模态能力是报告导入的核心依赖，无法用本地 LLM 替代；但文字咨询可以降级到本地 LLM，满足完全离线需求。

### D7: 单实例单家庭，不做用户体系

**决策**：MVP 不做多用户认证体系，单实例服务一个家庭，家庭内成员通过档案 ID 隔离数据。

**理由**：降低部署门槛和复杂度；开源项目 fork 者若需多家庭，可自行扩展。

### D8: 健康画像数据模型字段级定义

**决策**：为 A-H 每个字段族定义逻辑字段级模型，明确字段名、类型、单位、是否时序。此为逻辑模型，物理 schema（表结构、索引、关系约束）待技术选型（存储引擎确定）后落地。

**A 基础信息**（非时序，每成员一行）

| 字段名 | 类型 | 单位 | 说明 |
|--------|------|------|------|
| 姓名 | string | — | 家庭成员姓名 |
| 性别 | enum | — | male/female/other |
| 出生日期 | date | — | 用于年龄计算 |
| 身高 | number | cm | 手动录入或报告抽取 |
| 体重 | number | kg | 时序记录见 B，此处存最新值快照 |
| BMI | number | — | 计算字段：体重(kg) / 身高(m)²，由系统计算 |
| 血型 | enum | — | A/B/AB/O，可附 Rh 正负 |

| 单位 | string | — | — | 如 mmHg/mmol/L/mg/dL |
| 参考范围下限 | number | — | — | 来自参考范围数据表（见 D9） |

| 测量时间 | datetime | — | ✓ | 实际测量时间 |

| 来源类型 | enum | — | — | manual/report/chat_extract |

**D 用药记录**（非时序，每条用药一行）

| 字段名 | 类型 | 单位 | 说明 |
|--------|------|------|------|

| 严重程度 | enum | — | mild(轻度)/moderate(中度)/severe(重度) |
| 记录时间 | date | — | 记录入档日期 |

|--------|------|------|------|

| 疾病名称 | string | — | 家族成员所患疾病 |

| 字段名 | 类型 | 单位 | 说明 |
|--------|------|------|------|
| 来源类型 | enum | — | manual(手动)/report(报告)/chat_extract(聊天抽取) |
| 采集时间 | datetime | — | 数据入档时间 |

**理由**：PRD 评审指出 A-H 字段族是概念分类而非可建表的 schema，工程师无法直接落地。字段级定义消除模糊性，让开发可以直接映射为物理表结构。逻辑模型与物理 schema 分离，避免在技术选型未定时过早绑定存储实现。

### D9: 参考范围数据来源与管理

**决策**：维护一份本地化的医学参考范围数据表，以 JSON 配置文件形式版本化管理，覆盖第一梯队指标（血压、血糖、血脂、心率、BMI）。参考范围按性别 + 年龄段分组，因多项指标参考范围存在性别和年龄差异。

**数据结构示意**：

```json
{
  "version": "1.0.0",
  "updated_at": "2026-07-22",
  "sources": [
    "《中国成人血脂异常防治指南（2023年修订版）》",
    "《中国高血压防治指南（2024年修订版）》",
    "《中国2型糖尿病防治指南》"
  ],
  "ranges": {
    "systolic_blood_pressure": {
      "unit": "mmHg",
      "groups": [
        { "gender": "any", "age_min": 18, "age_max": 64, "lower": 90, "upper": 120 },
        { "gender": "any", "age_min": 65, "age_max": 120, "lower": 90, "upper": 130 }
      ]
    },
    "fasting_glucose": {
      "unit": "mmol/L",
      "groups": [
        { "gender": "any", "age_min": 18, "age_max": 120, "lower": 3.9, "upper": 6.1 }
      ]
    }
  }
}
```

**管理规则**：
1. 参考范围数据表纳入版本控制，每次更新记录版本号、更新时间、变更说明
2. 每条参考范围标注数据来源（具体指南或医学文献名称）
3. 运行时根据成员性别 + 年龄动态匹配对应分组，未匹配到则使用默认分组并标注"参考范围缺失"
4. 用户可在设置中查看当前参考范围数据表版本及来源

**⚠ 需医学团队确认**：参考范围的准确性直接影响异常判定和用户健康提示，所有数值需医学专业人员审核后方可纳入正式版本。当前 JSON 中的数值为占位示例，不可直接用于生产。

**理由**：PRD 评审指出 visualization 和 ai-consultation 都依赖参考范围做异常判定，但数据来源完全未定义，属于医疗合规的关键缺口。硬编码在代码中不可维护且无法版本追踪；大模型判断不可靠。本地 JSON 配置文件方案在可维护性、可审计性、版本化之间取得平衡，且明确标注"需医学团队确认"以划清工程实现与医学判断的边界。

### D10: 结构化存储与向量库的数据流向

**决策**：明确同一份健康报告在结构化存储与向量库中的数据流向、各自存储内容、关联方式和查询路由。

**数据流向图**：

```
                         ┌─────────────┐
                         │  原始报告    │
                         │ (图片/PDF)   │
                         └──────┬───────┘
                                │
                                ▼
                         ┌─────────────┐
                         │  多模态抽取  │
                         │  (模型API)   │
                         └──────┬───────┘
                                │
                   ┌────────────┴────────────┐
                   │                         │
                   ▼                         ▼
          ┌─────────────────┐      ┌──────────────────┐
          │  结构化 JSON     │      │  原始文本 +      │
          │  (指标/诊断/    │      │  抽取摘要        │
          │   用药/过敏等)  │      │  (自由文本)      │
          └────────┬────────┘      └────────┬─────────┘
                   │                         │
                   ▼                         ▼
          ┌─────────────────┐      ┌──────────────────┐
          │  结构化存储表    │      │  向量库          │
          │  (B/C/D/E/F/G   │      │  (embedding +    │
          │   字段族)       │      │   原文存储)      │
          └────────┬────────┘      └────────┬─────────┘
                   │                         │
                   │                         │
          ┌────────▼────────┐      ┌────────▼─────────┐
          │ 可视化 / 指标查询│      │ AI 咨询语义检索  │
          │ 趋势图 / 异常标识│      │ (RAG)            │
          │ 精确数值查询     │      │ 上下文召回        │
          └─────────────────┘      └──────────────────┘
```

**关联方式**：结构化版本与向量化版本通过报告 ID（report_id）关联。每条结构化记录的溯源信息（H 字段族）中的 `原始文件ID` 即为 `report_id`；向量库中每条向量同样携带 `report_id` 元数据。查询任一侧可通过 `report_id` 定位到另一侧的完整数据。

**查询路由规则**：
1. 可视化、指标趋势、异常标识、精确数值查询 → 走结构化存储表
2. AI 咨询的语义检索（"我上次体检报告里肝脏那部分怎么说的"）→ 走向量库 RAG
3. AI 咨询的精确查询（"我最近血压多少"）→ 走结构化存储表（通过工具调用）
4. 意图路由器根据意图类型决定路由方向，同一咨询可能同时触发两路查询

**理由**：PRD 评审指出 D2 虽定义了"结构化为主 + 向量化辅助"的方向，但两者如何关联、各自存什么、查询时先查哪个均未明确。本决策补充数据流向图和关联机制，消除实现时的歧义，确保开发时两条数据通路职责清晰、可追溯。

## Risks / Trade-offs

- **[多模态抽取准确率]** 大模型对医疗报告的结构化抽取可能不准（指标名、数值、单位识别错误）→ 抽取结果必须经用户确认后入档；提供"编辑修正"入口；对关键字段（指标值）做格式校验
- **[AI 咨询安全风险]** 健康类 AI 回答可能误导用户（如用药建议错误）→ 角色知识边界明确声明不替代医生；高风险意图（用药咨询、症状咨询）回答必须附带免责声明；建议用户就医
- **[模型 API 依赖]** 多模态 API 挂掉或限流时报告导入瘫痪 → 降级提示"多模态服务暂不可用"；已入档数据不受影响，文字咨询可切本地 LLM
- **[飞书渠道接入门槛]** 需要用户自建飞书机器人、配置回调 → 提供详细配置文档；飞书渠道为可选模块，不影响 WebUI 核心功能
- **[报告归属误判]** 多模态姓名识别可能匹配错家庭成员 → 入档前展示归属确认；用户可随时修正归属
- **[隐私边界混淆]** 用户可能误以为"本地部署=完全不出网"，但模型 API 调用会发送对话内容 → 隐私声明必须明确区分"数据存储本地"与"模型推理在云端"；提供本地 LLM 选项作为完全离线方案
- **[内容安全风险分级]** AI 生成的健康建议无风险分级，可能输出高风险内容（如建议停药、开具处方）→ 引入内容安全标签体系（参考晓医 S/A/B 分级：S 级禁止输出、A 级高风险需警示、B 级常规），对用药咨询和症状咨询的输出做风险标记
- **[高危信号主动预警]** 当 AI 识别到高危健康信号（如胸痛描述、收缩压 >180 的临界血压值、急性症状）时，仅回答不够，需主动建议就医 → 在 ai-consultation 中增加高危信号检测，触发时回答优先推送"建议立即就医"提示，而非仅附带免责声明
- **[模型 API 数据留存政策]** 不同模型 provider 对发送内容的数据留存政策不同，用户健康数据可能被云端留存 → 文档中提示用户关注所选 provider 的数据政策；推荐支持"零数据留存"模式的 provider；本地 LLM 作为完全离线方案
- **[参考范围医学审核]** 参考范围数据需医学专业人员审核后方可用于异常判定 → 标记为"需医学团队确认"事项；MVP 阶段参考范围数据来源需在文档中标注并声明"仅供参考"，不作为诊断依据

## Migration Plan

全新项目，无迁移。部署步骤：
1. clone 仓库，配置 .env（模型 API key、飞书 Bot 凭证等）
2. docker-compose up 一键启动
3. WebUI 首次访问，创建家庭、添加成员
4. 开始录入数据或上传报告

回滚：停掉容器即可，数据在本地卷中保留。

## Technology Decisions

以下技术选型于 2026-07-22 技术讨论中确定，替换原 Open Questions 章节。

### TD1: 技术栈 — Python + FastAPI + React

**决策**：后端 Python 3.12 + FastAPI，前端 React 18（Vite 构建）。

**理由**：
- Python 的 AI/LLM 生态碾压级优势（openai SDK、LangChain、LlamaIndex 均为 Python 第一公民）
- 多模态和 PDF 处理生态成熟（Pillow、PyMuPDF、pdfplumber）
- 向量库 SDK 全覆盖（pgvector、Chroma、Qdrant 均有 Python 原生支持）
- Python 是 AI 开源项目的事实标准语言，目标开发者群体熟悉
- 代价是前后端两套语言，但 AI 能力的权重远大于前后端统一

**备选方案**：Node/TS 全栈（前后端统一但 AI 生态弱）、Go（部署轻但 AI/PDF 生态弱）——均被否。

### TD2: 结构化存储 + 向量库 — Postgres 16 + pgvector

**决策**：PostgreSQL 16 + pgvector 扩展，一套数据库同时承载结构化存储和向量检索。ORM 用 SQLAlchemy 2.0，数据库迁移用 Alembic。

**理由**：
- 事务一致性：D10 定义"一份报告同时写结构化表和向量库"，pgvector 在单库 ACID 事务内保证同时提交或同时回滚，避免分体式数据不一致
- 关联查询原生支持：report_id 关联变成外键 JOIN，应用层不写跨库逻辑
- 单家庭数据量小（百级向量），pgvector 性能充裕，专用向量库的优势在百万级才体现
- 部署简单：docker-compose 只需一个 Postgres 服务
- 2 期扩展多家庭时，Postgres 天然支持

**备选方案**：SQLite + Chroma（分体式，事务一致性难保证）、SQLite + Qdrant（同上）——均被否。

### TD3: 多模态抽取 JSON Schema — 预定义通用 schema

**决策**：定义一套通用 JSON Schema 覆盖所有报告类型，模型按 schema 输出结构化 JSON（structured output / function calling 强制格式）。

**Schema 结构**：
- `report_type`：区分报告类型（lab_test / prescription / exam_report / medical_record）
- `patient_name`：报告上的患者姓名（用于归属匹配）
- `items[]`：结构化条目数组，每条含 `category`（metric/diagnosis/medication/allergy/lifestyle）和统一 `fields` 结构
- `raw_summary`：整体文本摘要（走向量库）

**理由**：
- 一套 schema 覆盖所有类型，不需要按报告类型分别定义
- `items[].category` 直接映射 D8 字段族，应用层按 category 分发到对应表
- `free_text` 字段兜底无法结构化的内容，不丢信息
- structured output 保证格式可靠，直接落库不用清洗
- provider 不支持 structured output 时，降级为自由输出 + 后处理校验

**备选方案**：自由输出 + 后处理校验（灵活但格式不可靠，边界 case 多）——被否。

### TD4: 意图路由 — function calling 一体化

**决策**：不单独实现意图分类器，而是将六个工具定义（query_metrics / query_profile / query_abnormal / interpret_metric / extract_and_save 等）直接通过 function calling 传给大模型，模型在一次请求内自行决定调用哪个工具。意图路由与工具调用合并为一步。

**理由**：
- 一次请求完成意图路由 + 工具调用，省一次 round trip，延迟降一半
- function calling 是大模型标准能力（OpenAI/讯飞/DeepSeek/Ollama 均支持），准确率高于自写分类 prompt
- 聊天抽取意图天然支持——模型自然决定调 extract_and_save
- 超出能力的问题模型不调工具，走 system prompt 角色边界约束，自然兜底
- MVP 不加规则层；后续高频意图如延迟敏感可加规则前置拦截，但属优化非必需

**备选方案**：
- 纯大模型意图分类（多一次调用，延迟+成本）——被否
- 纯规则匹配（死板，聊天抽取意图几乎无法做）——被否
- 混合规则+模型（两套逻辑维护，MVP 不需要）——保留为后续优化方向

### TD5: 飞书渠道接入 — 企业自建应用

**决策**：用户需在飞书开放平台创建企业自建应用，添加机器人能力，配置消息回调地址。自建应用不需飞书官方审核，仅需企业管理员审批。个人用户可创建免费企业，自任管理员自行审批。

**所需权限**：`im:message`（接收消息）、`im:message:send_as_bot`（发送消息）、`im:resource`（接收图片/文件）。

**影响**：不阻塞架构设计。V0.4 飞书渠道配置文档中将提供详细步骤指引。
